# Extraction eval

Compares the four extractors that can turn a remote job posting into structured fields, on the
same 40 hand-labelled jobs. Results: `report.md` (full), `../../web/public/data/eval.json`
(what the dashboard's Methodology page reads), `review.md` (checklist for reviewing the labels).

| Extractor | Backend / model tag |
|---|---|
| Claude Sonnet 5.5 | `claude` / `claude-sonnet-5-5` |
| Gemma 4 12B | `ollama` / `gemma4:12b` |
| Qwen 3.8 27B | `ollama` / `qwen3.8:27b` |
| Gemma 4 31B (Q4_K_M) | `ollama` / `gemma4:31b-it-q4_K_M` |

## Files

| File | What |
|---|---|
| `gold.jsonl` | The gold set: one JSON object per job (frozen `JobInput`, labels, notes). **Edit labels here.** |
| `build_gold.py` | Seeded selection (`select`), printing postings as the model sees them (`show`), merging hand-written labels (`merge`). |
| `labels_draft/*.json` | The raw hand-written labels (before skill canonicalisation) that `merge` turned into `gold.jsonl`. History only. |
| `run_eval.py` | `run` (call a model, cache raw results) and `score` (re-score caches, write reports). |
| `scoring.py` / `reporting.py` | Pure metric functions and markdown rendering. |
| `test_scoring.py` | Unit tests of the metrics on toy data. |
| `runs/*.jsonl`, `runs/*.meta.json` | Cached raw model outputs (data, ok, error, latency, tokens, cost) and per-run hardware notes. |
| `report.md`, `review.md` | Generated by `score`. |

## Commands (from `pipeline/`)

```
uv run python eval/run_eval.py run --backend ollama --model gemma4:12b [--limit N] [--resume] [--retry-failed]
uv run python eval/run_eval.py run --backend claude --model claude-sonnet-5-5   # needs ANTHROPIC_API_KEY
uv run python eval/run_eval.py score          # no model calls; relabelling is free
uv run pytest eval/test_scoring.py -q
```

`run` refuses to touch an existing cache unless you pass `--resume` (skip cached jobs) or
`--overwrite`, so a paid Claude run cannot be wiped by accident. Claude runs abort if the spend
would exceed `--max-cost` (default USD 2.00). Ollama runs make one unscored warm-up call (so
model-load time is not in the per-job latency), record how much of the model sits in VRAM, then
`ollama stop` the model.

## How the 40 jobs were chosen

Seed `20261106`; code in `build_gold.py` (`select_jobs`), run once against `data/jobs.sqlite` on
2026-11-06 and then frozen in `gold.jsonl` (the DB grows nightly, so re-running `select` later
would pick different jobs; it refuses to overwrite without `--force`).

1. **Pool:** canonical (`is_duplicate_of IS NULL`), remote jobs with a description of at least
   200 characters, and without an inline base64 image in the first 6,000 characters (one RemoteOK
   posting was excluded: its whole visible text was an image blob). 447 jobs.
2. **Stratification flags** use cheap rules, never a model: a role bucket from title keywords; a
   stopword-based non-English test; a regex for a currency amount near salary words in what the
   model will see; description length of at least 8,000 characters = "long".
3. **Greedy quotas over a seeded shuffle**, in this order: 3 non-English; one posting for every
   distinct currency/period combination found, topped up to 9 salaried; 4 long; at least 2 for
   each role bucket except software engineering; at least 6 per source; then fill to the
   per-source targets Remotive 7 (nearly the whole source), Arbeitnow 8, Remote OK 12, Jobicy 13.
4. **Result:** 13 Jobicy, 12 Remote OK, 8 Arbeitnow, 7 Remotive. Gold role mix: 9 software
   engineering, 7 support, 6 other, 4 sales, 3 data, 3 management, 2 each design, marketing,
   product and devops/SRE. 16 jobs state a salary in the text the model sees (USD/GBP/EUR/AUD/CAD;
   year, month and hour). 3 postings are German (Arbeitnow also has English ones). 4 have
   descriptions over 8,000 characters. One is a deliberate "nothing to extract" posting.

Engineering is under-represented relative to the real feed on purpose (the brief asked for a
spread of roles); do not read the headline numbers as "accuracy on the average posting".

## How the labels were made

A Claude model (Sonnet 5.5, the same family as one of the contestants) read each posting as
`build_gold.py show` prints it, i.e. exactly what an extractor receives, and applied the
definitions in `src/radar/extract/prompts/extract.md` literally. **All 40 label sets were
written before any model was run, and no model output was looked at while labelling.**
Every label set has `"status": "draft"` and a `notes` field. Skills were written as free text and
passed through `normalize_skills`, so gold and predictions share one vocabulary.

Judgement calls worth knowing:

- Labelled from the text the extractor sees, i.e. truncated to 6,000 characters, not from the
  full posting.
- Where the salary line and the body disagree, the salary line wins; where a posting gives two
  currency bands, the USD one is labelled; OTE is labelled only if it is the sole figure.
- A level the prompt does not map (director, "Engineer III") is `unspecified` unless the prompt's
  own analogy applies (director treated like "head of" -> lead). These cases are flagged.
- 21 of 40 label sets contain the word `AMBIGUOUS` in their notes: the labeller saw two
  defensible answers. `report.md` shows accuracy on the clear and the ambiguous subsets
  separately.

## Limitations (please read before quoting numbers)

1. **Same-family bias.** The annotator is a Claude model, so the labels may favour the Claude
   extractor. The user must review the labels (`review.md`) before the numbers are published as
   final; relabelling is free (`score` makes no model calls).
2. **n = 40.** One job moves accuracy by 2.5 points. `report.md` gives bootstrap intervals
   (1,000 resamples, seed `20261106`) and paired intervals for differences between models.
3. **One run per model.** Ollama runs at temperature 0; Claude Sonnet 5.5 accepts no sampling
   parameters, so its run is not guaranteed repeatable.
4. **Hidden structured salaries.** `extract_stage.job_input` passes `salary_text` (set for
   Remotive only) and the description. Jobicy and Remote OK structured salaries are not shown to
   the model (5 gold jobs have one that the text does not state). Salary accuracy therefore
   measures extraction from prose, not what the nightly pipeline publishes.
5. **Alias table collisions.** `normalize_skills` merges some distinct tools (for example n8n
   -> zapier, zoom -> slack, gitops -> helm, delta lake -> databricks, pgvector ->
   vector-database). It affects gold and predictions equally, but it blurs the skills metric.
6. **Latency is not comparable across backends.** Claude's number is an API round trip; local
   numbers depend on the GPU, the ~12 GB held by desktop apps, and any CPU offload (recorded in
   the `.meta.json` files and summarised in `report.md`).

## Data availability

`gold.jsonl` contains the full text of each posting exactly as the models saw it. Job ads belong to the companies and boards that published them, so that file is kept out of the public repository. `gold.public.jsonl` is the same 40 records with the description text removed: job id, source, link to the original posting, title, company, labels and selection metadata. `run_eval.py score` reads it automatically when the full file is absent, so every number in `report.md` can be reproduced from the committed model outputs in `runs/`. Re-running the models needs the full file, which `build_gold.py` rebuilds from your own pipeline database.
